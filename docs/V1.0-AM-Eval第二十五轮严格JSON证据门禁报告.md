# AM-Eval 第二十五轮：严格 JSON 证据门禁报告

## 1. 结论

第二十五轮消除了 AM-Eval 证据链中的 JSON 重复键歧义。此前只有正式 run 的末端解析路径显式拒绝
重复键，数据集、execution plan、scorer 输入、typed attestation 内嵌结果等入口仍有各自的
`json.loads`。标准解析器会静默采用最后一个同名字段，因此同一份字节可以同时展示两个 `run_id`、
`model` 或治理标志，造成评审界面、签名工具和实际执行器理解不一致。

修复后，所有 AM-Eval JSON 入口统一调用一个严格解码器：递归拒绝重复键、非有限数值、非 UTF-8
输入和非对象顶层。攻击性回归覆盖了数据集嵌套对象和 typed attestation 的内嵌 scorer result。
本轮不更新正式指标，决定仍为 `INCOMPLETE`。

机器证据见
[`../benchmarks/am-eval-v1/round-25-strict-json-evidence-gate.json`](../benchmarks/am-eval-v1/round-25-strict-json-evidence-gate.json)。

## 2. 修复前复现

对以下字节使用原标准解析器：

```json
{"run_id":"shadow","run_id":"hermes:automated-tests:formal"}
```

解析成功，最终 `run_id` 为第二个值。也就是说，旧入口会接受一份在视觉审查时可被理解为
`shadow`、在 Python 执行时却被理解为正式 run 的输入。该行为不是哈希碰撞：文件 SHA 可以完全一致，
歧义来自解析语义本身。

## 3. 统一严格解码合同

共享 `decode_strict_json_object` 现在要求：

1. 输入必须是 UTF-8；
2. 输入必须是合法 JSON，且顶层必须是对象；
3. 任意嵌套层级不得出现重复键；
4. `NaN`、`Infinity`、`-Infinity` 不得进入证据对象；
5. 调用方继续执行自身 exact-schema 与类型校验，严格解码不替代领域合同。

已迁移的入口包括冻结数据集 manifest/JSONL、官方 spec、正式 run、build identity、execution plan、
atomic quality、efficiency、typed attestation、deterministic bundle、reliability receipt 和 recall API 响应。
源码检索确认 AM-Eval 模块中只剩共享解码器内部调用 `json.loads`。

## 4. 攻击性回归

以下输入均被拒绝：

- 数据集 manifest 的嵌套对象出现重复键；
- attestation 组装时，内嵌 atomic quality result 含两个 `run_id`；
- typed source-result validator 读取同一歧义结果；
- 正式 run 顶层出现两个 `benchmark_id`。

后两类验证保证攻击者不能先生成一个有效 scorer result，再通过重复身份字段把它包装成另一条正式证据。

## 6. 保留边界

严格 JSON 不能证明结果文件在生成后未被修改；不可变 artifact storage、签名或 attestation 仍需单独
建立。GHCR manifest 的远端 provenance 也不能由本地 source SHA 替代。

本轮没有启动数据库、API、worker，没有调用外部模型，没有读取记忆正文，也没有连接或修改生产环境。
M01、M02、M03、M07、M22、M23 仍未完成正式测量，`release_ready=false`。
