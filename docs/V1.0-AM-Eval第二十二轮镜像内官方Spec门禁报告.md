第二十二轮把第 21 轮的官方 spec 来源规则放入当前 clean revision 构建的真实本地镜像，并在
`--network none`、只读根文件系统、非 root 用户和资源限制下验证实际 CLI 路径。

结果：

- 镜像 build identity/runtime identity：PASS；
- 官方 spec 原始 SHA + 语义 SHA：PASS；
- 官方 spec 通过后继续到 run schema 校验：PASS；
- 自证自身 SHA 的宽松伪造 spec：CLI exit 2，REJECTED；
- 传入官方 SHA 的伪造 spec：语义摘要门禁 REJECTED；
- 本地测试镜像、容器和输入目录：已删除；
- 正式指标不更新，决定仍为 `INCOMPLETE`。

## 4. 实际 CLI 攻击验证

### 4.1 官方 spec

官方文件在镜像代码中登记：

- artifact SHA：`a4ce9232ecafc37f9a3142a8e29020168af96aa6b4165e21fd64395186c7b679`；
- semantic SHA：`b25f605699051d7a611afbaeb9a31a0a6de46ef342b5a2be88b898b917f10a80`。

直接双摘要检查返回 PASS。随后实际 `agent-memory-benchmark` 使用官方 spec 和一个刻意不完整的 formal
run，错误停在 `formal AM-Eval run has an invalid schema`。这证明 spec 已通过官方门禁，后续仍按 run
schema fail-closed。

### 4.2 自证宽松 spec

伪造文件保留 `benchmark_id=am-eval-v1`，但删除全部硬门禁、只保留一个 100 权重指标，并把发布最低分
改为 0。操作员传入该文件自身真实 SHA：

`802a14af812d066bafef16ec39850b093621a0a5796c7fc7d2bf3c672b970d07`

实际 CLI 在读取 artifact 或运行 scorer 前 exit 2：

`formal AM-Eval official specification SHA-256 confirmation mismatch`

再以官方 SHA 绕过第一层的直接函数攻击也被第二层语义摘要拒绝：

`formal AM-Eval specification semantics differ from the official contract`
