# AM-Eval 第二十三轮：正式身份归属门禁报告

## 1. 结论

第二十三轮发现并修复了一个正式评估来源归属漏洞：有效的 Agent Memory scorer 结果可以保留内嵌原始
字节，只重写 formal run 的系统名称与外层 OCI repository，再重算 artifact/run SHA，就得到
`decision=PASS`、`release_ready=true`，结果却显示为其他系统。

修复后：

- 正式系统名称必须精确为 `agent-memory`；
- 正式执行仓库必须精确为登记的 `ghcr.io/evergardener/agent-memory-api`；
- typed attestation 组装器、确定性多数据集 run 组装器和最终 evaluator 使用同一登记合同；
- 系统改名与仓库改绑攻击均 fail-closed；
- 正式指标未更新，决定仍为 `INCOMPLETE`。

机器证据见
[`../benchmarks/am-eval-v1/round-23-formal-identity-attribution-gate.json`](../benchmarks/am-eval-v1/round-23-formal-identity-attribution-gate.json)。

## 2. 修复前攻击复现

攻击保留质量 scorer result 内嵌的：

- 原始 JSON 字节与 SHA；
- Agent Memory revision、source SHA、environment SHA；
- dataset、execution plan、计数和指标；
- `model_called=true` 与 private-blind 声明。

仅修改：

- `run.system.name`：`agent-memory` → `honcho`；
- `execution_artifact.image_name`：Agent Memory API 仓库 → `ghcr.io/example/honcho`；
- artifact/run 外层对应绑定和 SHA。

修复前实际返回：

```json
{
  "decision": "PASS",
  "release_ready": true,
  "claimed_system": "honcho",
  "claimed_image": "ghcr.io/example/honcho"
}
```

这说明既有来源摘要证明了“内容一致”，却没有证明“结果归属于哪个被评系统和登记仓库”。

## 3. 实施规则

新增单一正式合同 `am_eval_formal_contract.py`，登记：

- `OFFICIAL_SYSTEM_NAME=agent-memory`；
- `OFFICIAL_EXECUTION_IMAGE_NAMES={ghcr.io/evergardener/agent-memory-api}`。

执行层次：

1. typed attestation 组装时拒绝其他 repository；
2. 五类确定性 artifact 组装正式多数据集 run 时再次拒绝；
3. 最终 evaluator 同时核对 system name 与 execution image repository。

修复后的真实攻击脚本返回：

```json
{"attack":"system-name-laundering","status":"REJECTED","reason":"formal run system identity must identify agent-memory"}
{"attack":"image-repository-laundering","status":"REJECTED","reason":"formal run requires a registered Agent Memory execution image"}
```

## 5. 保留边界

本轮证明系统名称和 OCI repository 不能被外层重写，但不声称仅靠进程内代码能证明实际运行的 manifest
digest。正式执行仍必须由外部流程按 `name@sha256:<digest>` 拉取、验证 provenance/attestation，并从该
digest 启动评分器。

本轮没有启动数据库、API、worker，没有调用外部模型，没有读取记忆正文，也没有连接或修改生产环境。
M01、M02、M03、M07、M22、M23 仍未完成正式测量，`release_ready=false`。
