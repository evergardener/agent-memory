# Agent Memory V1.0 生产试运行治理改进计划

> 基线日期：2026-08-06  
> 生产基线：`1.0.0-rc.8`，revision
> `f7a93e9297c224f1b9cbf766ac53bd6042979be5`，状态 `canary_active`。  
> 输入：生产试运行反馈 `AGENT_MEMORY_GOVERNANCE_PLAN.md`、当前源码、只读生产聚合数据。  
> 本文只授权需求冻结与开发规划；不授权生产数据迁移、失败任务重放、历史清理、容器更新或
> Hermes 配置修改。

## 1. 评估结论

附件的总体方向正确，四项用户问题均成立，但实现方案必须复用现有数据模型，避免再建立一套
准入、生命周期或审计体系。

| 问题 | 结论 | 当前根因 | 优先级 |
| --- | --- | --- | --- |
| Current State resolve 后仍可浏览 active current fact | 已确认 | `resolve` 只更新 `state.current_items`；关联 `memory.facts` 和 `retrieval.documents` 未同步 | P0 |
| 一次性内容进入 Current State | 已确认 | `CURRENT_PATTERN` 将“今天”、设备开关等宽泛信号直接判为 active current；缺少“未完成、可续接、近期相关”门禁 | P0/P1 |
| preference 没有形成可用数据 | 已确认 | preference 表和 API 已存在，但生产为 0；当前解析只覆盖“我喜欢/偏好”等窄语式，不覆盖“以后称呼我为……”等显式偏好 | P1 |
| 宽泛改写漏召回、随机输入误命中 | 已确认存在架构风险 | 当前所谓 semantic 通道是 `local-hash-v1` 的 32 维字符/词哈希，并非语义模型；RRF 输出没有最终 `min_score/min_margin` 门禁 | P1 |
| 永久清除失败 | 附件未覆盖，生产新增发现 | 2 个 `purge_memory` 因 `RestrictViolation` 终止，新增统一记忆外键未进入完整删除/脱离顺序 | P0 |
| 模型任务超时后形成治理盲点 | 附件未覆盖，生产新增发现 | 1 个 `extract_atomic_turn` 在 5 次 `Timeout` 后进入 failed；证据仍保留，但没有受控重放和未确认失败 Gate | P0 |

## 2. 2026-08-06 生产只读基线

实际 Hermes Provider 使用 `http://127.0.0.1:7810`；附件中的 `7788` 是默认/旧示例，不是当前
生产端口。生产模型为 `openai/ocg/qwen3.7-plus`，仅允许脱敏数据，历史自动回填关闭。

| 指标 | 只读结果 | 解释 |
| --- | ---: | --- |
| evidence events / facts | 12,217 / 107 | 生产验证 PASS，数据持续写入 |
| Current State | active 1 / expired 1 / resolved 20 | Current State 本身能正确 resolve/expire |
| active current facts | 20 | 其中并非都仍可作为当前上下文 |
| resolved item 仍关联 active fact | 5 | 直接证明 P0 生命周期不一致 |
| expired item 仍关联 active fact | 1 | 到期维护只改 state item |
| active current fact 无 state item | 13 | 其中 8 条已过 `valid_to`，5 条仍在未来有效期 |
| active current 设备瞬时状态 | 17 | 一次性 Home Assistant/开关状态是主要污染源 |
| preference assertions | 0 | schema 存在，但生产提取链未形成可用偏好 |
| 原子模型任务 | done 29 / failed 1 | 29 个成功任务对应 10 次 applied、19 次 no-candidates |
| 模型准入决策 | accept 18 / review 0 | 需要金标复核，不能据此直接判断准确率达标 |
| purge 任务 | done 61 / failed 2 | 永久清除路径存在真实外键回归 |

`production-verify ... runtime existing` 当前会报告 `failed_jobs=3` 但仍返回 PASS。运行存活验证与
质量/治理 Gate 的语义需要分开：运行态可以 fail-soft，但生产晋级不得忽略新增未确认失败。

## 3. 对附件实现建议的取舍

### 3.1 直接采纳

- Current State 的 `resolved/expired` 不得进入默认 browse/recall；证据与审计继续保留。
- 自动 current 必须同时满足“未完成、近期相关、后续可续接”的明确门禁。
- prompt、工具参数、模型切换、已完成动作、单次设备遥测默认 evidence-only。
- 显式偏好可直接 active；隐式行为只能 candidate，冲突使用替代链。
- 召回增加输入质量、最终分数、margin 和 `no_match` Gate。
- 所有历史治理先 dry-run、恢复验证备份、影响清单，再单独授权 apply。

### 3.2 调整后采纳

1. **不新增第二套准入枚举。** 继续使用
   `discard/evidence_only/accept/review`；另设 `target_kind` 表达
   `fact/current/preference/episode/procedure/...`。准入决策、目标类型和生命周期是三个正交维度。
2. **不在 fact 上复制 `current_state_status` 作为第二权威。**
   `state.current_items` 是 Current State 权威；browse/trace 可以返回派生的
   `current_state_status`。resolve/expire 事务同时把关联 current fact/document 降为 dormant。
3. **不增加通用 `recall_eligible` 布尔值。** 召回资格由对象生命周期、Current State 状态、
   `valid_to` 和请求 intent 统一计算，避免布尔值与状态再次漂移。
4. **不另建通用治理审计表。** 复用 `audit.events`，补齐 `policy_version`、before/after、
   source IDs 和批次 manifest 元数据。
5. **preference schema 不重建。** 复用 `memory.preference_assertions` 的 explicitness、state、
   supersedes 和 version；补充多证据关联、显式称呼/风格解析和 API 溯源字段。
6. **USER memory 不自动回写。** V1 只提供差异预览/导出建议；任何同步都必须由用户明确批准，
   且不能覆盖人工维护的 USER memory。

### 3.3 暂不采纳

- 未经评测直接把当前聊天模型同时用于 embedding 或 rerank。
- 根据文本相似度自动物理删除历史记录。
- 直接编辑 managed 的 `jiuyue/plugins/agent_memory/provider.py`。
- 在未完成真实金标前批量重判现有 current/candidate。

## 4. 冻结后的统一治理语义

每条输入依次经过四个正交层次：

```text
evidence retention
  -> admission: discard | evidence_only | accept | review
  -> target kind: fact | current | preference | episode | temporal_rule | procedure | ...
  -> lifecycle: candidate | active | dormant | superseded | forgotten | isolated
```

Current State 使用独立状态机：

```text
active -> resolved | expired
```

约束：

- `current_item=resolved|expired` 时，关联 current fact/document 默认必须 dormant；
- 审计/trace 可以看到历史，但普通 browse/recall 不得返回；
- 手工 Current State 可以没有 `source_fact_id`，但自动 Current State 必须有稳定关联；
- `valid_to <= now()` 是召回层硬门禁，即使维护任务延迟也不得返回；
- 模型超时只留下 evidence-only 和失败审计，不自动生成 candidate；受控重放是独立操作。

## 5. 后续开发阶段

### H0：运行失败与基线收口（P0）

目标：先保证治理动作和模型失败是可见、可恢复、可阻断晋级的。

1. 将附件回归样本、当前聚合 SQL 和生产 revision 固化为只读 baseline manifest。
2. 在生产备份副本复现 2 个 `RestrictViolation`，修正 fact 清除前对 episode、preference、
   relationship、temporal rule、artifact、procedure、current item 和 retrieval 投影的依赖处理。
3. 增加失败模型任务的限定范围 dry-run/requeue 命令；默认拒绝全历史回放，保持
   `MODEL_AUTO_BACKFILL_ENABLED=false`。
4. 将运行健康与质量健康分开输出：`runtime` 可报告 degraded；canary/promotion 对新增、未确认
   failed job 失败关闭。
5. 增加模型成功率、超时、重试、终态失败和脱敏计数，不记录 prompt、响应正文或 key。

Gate：永久清除测试 100% 完成；模型超时不丢 evidence、不制造 candidate；指定任务重放幂等；
0 个未确认 P0 失败；恢复演练 PASS。

### H1：Current State / fact / index 生命周期一致性（P0）

1. 为 `state.current_items` 增加 `resolved_at`、`resolution_reason` 和乐观并发 `version`；沿用现有
   `source_fact_id`，不新增重复关联字段。
2. 实现唯一的事务化 transition service：set/update/resolve/expire 同步 current item、关联 fact、
   retrieval document 和审计事件。
3. browse/recall 增加防御性过滤：current fact 必须有效且没有 resolved/expired 关联；管理模式可用
   `include_resolved=true` 查看历史状态和原因。
4. 迁移仅对生产副本生成 dry-run：
   - 已关联 resolved/expired 的 active current fact 建议 dormant；
   - 已过 `valid_to` 的 unlinked active current fact 建议 dormant；
   - 仍有效但 unlinked 的 5 条逐条列出关联/隔离建议，不自动推断。
5. 修正 maintenance，使 expire 与 resolve 使用同一 transition service。

Gate：resolve 一致性误差为 0；新自动 current 关联覆盖率 100%；重复执行幂等；旧证据哈希、Vault
和非 current 事实计数不变；迁移可回滚到“不使用新字段”的旧代码。

### H2：Current 准入与一次性内容过滤（P0/P1）

1. 保留现有四态 admission，不引入 `ignore/event_only` 平行状态；过滤结果映射为
   `discard/evidence_only`。
2. 拆分宽泛 `CURRENT_PATTERN`：日期词和 `turned on/off` 不再单独证明“需续接”。
3. 默认 evidence-only：图片/编辑 prompt、skill 安装询问、模型切换、工具参数、已完成任务、单次
   Home Assistant 状态、一次性定时任务查询。
4. active current 必须满足三项中的至少两项，且“未完成”是必需项：
   - 明确未完成/暂停/等待/阻塞；
   - 近期仍相关；
   - 下一会话需要续接。
5. 模型/规则输出增加可审计的 `decision_reason`、`policy_version` 和 target kind；模型不能绕过
   Current State policy gate。
6. 先在隔离数据库运行 shadow replay，只记录新旧分类差异，不改变生产写入。

Gate：附件列出的 prompt、skill、模型切换、已完成任务和设备瞬时状态产生 0 active current；
“先暂停邮件提醒任务”仍进入 current；模型关闭/超时不产生 review 洪峰。

### H3：证据化 preference 链路（P1）

1. 扩展显式偏好语式：称呼、语言、表达风格、操作约束和提醒方式；覆盖“以后称呼我为公子”。
2. 为 preference 增加多 evidence 关联，API 返回 source IDs、explicitness、extraction method、
   confirmed state、替代链和版本。
3. 显式用户偏好可 active；单次行为只 candidate；重复证据只增加支持，不重复建记录。
4. 同一 `(subject, aspect)` 的冲突更新建立 supersedes 链，旧项不得继续注入。
5. 增加 USER memory 差异预览；V1 不自动写 USER memory。

Gate：显式偏好准确率目标不低于 95%；相反偏好不同时 active；跨 profile 共享只遵循当前单用户
shared namespace 产品边界，并保留来源，不把 profile 风格写成用户偏好。

### H4：召回输入质量、排序和语义能力（P1）

1. 对 UUID、哈希、纯数字、随机 token 和低信息查询禁用模糊 semantic 通道，除非 lexical/entity
   精确命中。
2. 增加版本化 alias/query normalization，先覆盖“邮件通知/邮件提醒”等金标同义表达。
3. 输出并校准 lexical、entity/relation、temporal、procedure、fuzzy/semantic、recency 和状态适用性
   子评分；最终加入 `min_score`、`min_margin` 与 `no_match`。
4. 将 `local-hash-v1` 明确标为 fuzzy hash，不再把它当作真实语义质量证据。
5. 单独 ADR 评估本地多语 embedding、受授权外部 embedding 或 rerank。任何新模型必须版本化索引、
   双读对比、可回滚；外发 embedding 是新的数据授权面。

Gate：紧密和宽泛邮件查询均命中正确 active 状态；resolved 后均 no-match；随机/无关 query 的
误命中率不高于 1%；金标 top-1 不低于 90%；低 margin 不注入 Hermes prompt。

### H5：历史治理债务 dry-run（P1/P2，独立数据授权）

1. 合并现有 G4 candidate dry-run 与 H1 current lifecycle dry-run，按对象类型分别出影响清单。
2. 输出建议动作、理由、证据、实体/情节/程序影响、前后计数、manifest SHA 和回滚点。
3. 先处理可证明的状态漂移与完全重复；语义相似、敏感、人物身份和冲突项继续人工治理。
4. candidate TTL 只改变默认可见性，不删除 evidence；具体 TTL 必须由真实分布评测后冻结。
5. apply 前创建新鲜恢复验证备份并再次取得用户批准。

Gate：dry-run 0 写入；apply 重放幂等；证据哈希和 Vault 不变；删除/脱离/忘记的派生重建完整；
人工 review 比例目标不高于 10%。

### H6：生产 canary 与晋级（独立部署授权）

1. H0–H5 在隔离 API/worker/PostgreSQL、浏览器和故障恢复 Gate 全部通过。
2. 指定 full SHA、不可变 GHCR 镜像、SBOM/attestation、迁移清单、停写窗口和回滚 revision。
3. 生产更新前后分别完成恢复验证备份；不修改 Hermes Agent 核心或 managed 插件目录。
4. 重新计算 2/24/72 小时窗口，观察：
   - resolve 一致性；
   - current 噪声率；
   - preference 精确率与冲突；
   - 召回 top-1、no-match 和跨 profile 边界；
   - 模型超时/费用、任务积压和 failed jobs；
   - 星图实体/关系与候选治理数量。
5. 用户完成星图、治理页、Current State 和跨 session 召回主观验收后，才可讨论
   `production_active`。

## 7. 最小回归与指标

| 场景 | 必须结果 |
| --- | --- |
| resolve 邮件提醒事项 | Current State 不显示；默认 fact browse/recall 不显示；trace 可见 reason/time |
| 图片 prompt / skill 安装询问 / 模型切换 | evidence-only；0 active current |
| 单次 Home Assistant 开关状态 | evidence-only；0 active current；不生成星图关系 |
| “先暂停邮件提醒任务” | active current，有 TTL、source fact 和审计 |
| “以后称呼我为公子” | active explicit preference，有 evidence；不自动写 USER memory |
| 偏好 A 后改 B | B active，A superseded，普通召回只注入 B |
| “暂停邮件提醒” | 命中 active 邮件事项 |
| “邮件通知目前是不是暂停了” | active 时命中；resolved 后 no-match |
| 随机 token / UUID / 无关自然句 | no-match |
| 模型超时 | evidence 保留，0 candidate 洪峰，可限定范围 dry-run/replay |
| 永久清除含统一派生对象的 fact | 无 RestrictViolation，审计与依赖处理完整 |
| profile/namespace 边界 | 无跨 namespace 泄漏；shared namespace 内保留来源 profile |

## 8. Review 与完成定义

每个批次必须按“需求/测试先行 → 实现 → migration/restore → 浏览器/故障 Gate → 独立 Review →
文档一致性”完成。以下任一情况阻断生产：

- resolved/expired current 仍进入默认上下文；
- 新增 `RestrictViolation` 或不可恢复数据操作；
- 模型失败导致证据丢失、candidate 洪峰或 Hermes 主回合失败；
- preference 冲突同时 active；
- 随机负向输入被默认注入；
- 新 embedding/rerank 未完成数据授权、版本化和回滚；
- 生产 failed job 未分类、未确认或无恢复方案；
- 最新备份未通过实际恢复和 Vault roundtrip。

在 H6 完成前，当前生产继续保持 `canary_active`，历史自动回填保持关闭，旧 candidate/current 不做
批量治理。
