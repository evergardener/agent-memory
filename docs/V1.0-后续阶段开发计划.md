# Agent Memory V1.0 后续阶段开发计划

> 基线：`1.0.0-rc.8`。截至 2026-07-26，生产 canary 运行 revision `e05a492…`，
> `main` 为 `d7f4016`；生产不会因主线变化自动更新。真实使用已确认 V1 的最终核心不能只停留在
> 基础事实/episode 和技术排障，而必须完成统一经历、纪念日、偏好演化和程序性记忆。
> 因此后续采用双轨：保持 rc.8 canary 稳定观察，同时在隔离分支完成阶段 F；最终 V1.0 晋级
> 增加 F0–F8 Gate，不用未完成的新模型直接改写生产数据。

## 1. 执行原则

- `main` 始终保持可部署；开发使用独立分支，只有完整 Gate 通过的提交才能作为生产候选。
- 真实 canary 从初始化起使用最终 project/data/Vault/namespace，通过后原地晋级，不再二次迁库。
- 显示名、布局和星系治理是用户信息架构，不得被当作世界事实或模型推理输入。
- 人工决定优先于后台自动结果；迁移、同步和重建不得覆盖用户改名或映射。
- 每一阶段都必须有可重复测试、审计记录、文档和回滚点；不以“视觉看起来正常”代替数据不变量验证。
- 需求、数据语义和验收场景先冻结，迁移/API/UI 后实施；任何 schema 设计不得通过代码反向定义产品语义。
- `source_profile`、经历主体和参与实体分开；模型与共同出现不能替代角色证据。
- 技术排障、旅行、人物关系、纪念日和偏好使用统一情节模型；程序性记忆只是经验证情节的派生层。
- 阶段 F 开发只使用隔离 namespace、合成数据和经授权脱敏样本；不读取或重建生产 namespace。

## 2. 阶段 E0：Subject 展示身份收尾（canary 前 P0）

实施状态（2026-07-22）：E0 代码、迁移、完整 Release Gate 和浏览器验收已完成。名称优先级为“人工名称 > 可读 `source_profile` > 未命名助手”，不解析 Hermes 私有配置文件。

| ID | 任务 | 完成标准 |
| --- | --- | --- |
| E0-01 | 名称来源数据模型 | 为 Subject 增加 `display_name_origin=default|source|manual`；默认值、约束、迁移和恢复测试完整 |
| E0-02 | 旧数据安全回填 | 已有 `subject.update` 人工名称标为 `manual`；内置 `User`/`Hermes · *` 转换不改变 ID、entity 或 source 映射 |

E0 已关闭。人工名不得被后续 profile ingest、来源策略或迁移覆盖。

## 3. 阶段 E1：真实 Hermes 多 profile、逐来源 canary（P0）

实施状态（2026-07-25）：首个 live source `jiuyue:production-jiuyue` 已通过 source-bound
验证并持续写入；历史 `qishuo:hermes-session-export` 已登记为 historical import，不能
满足 live gate。生产服务运行 rc.8 revision `e05a492…` GHCR 精确 SHA 镜像，模型关闭；
`jiuyue` profile Provider 已升级为 7 tools，最近记录 browse 与直接 recall 已验证。
当前回合重复采集和中文偏好召回缺陷已修复部署，但观察窗口必须以更新后真实使用重新核对；
最新恢复验证备份和人工质量验收仍是晋级前置条件。

1. 用户逐个指定真实 profile，同时确认每个 profile 的数据范围、模型范围、观察窗口和回滚点。
2. 从已推送且通过 handoff/Release Gate 的提交初始化唯一持久化生产资产；不复用 `/private/tmp` 演练目录。
   初始化、空库验证和备份恢复后必须运行 `production-canary-readiness.sh`，状态固定为 `AWAITING_USER_APPROVAL`。
3. 先在独立 `HERMES_HOME`/TUI 验证 Provider 发现、profile+instance 写入、跨会话召回、追溯和 API 断线 fail-soft。
4. 模型默认关闭。本地模型或脱敏外部 API 需单独授权和新生产 key，不复用历史测试 key。
5. 每个 live source 在首次 source-bound 验证后独立计算 2/24/72 小时；历史导入登记为 `historical_import`，不能满足 live gate。
6. 检查健康、任务失败、证据脱敏、召回越界、恒星名称、星图治理、日志轮转、磁盘增长和 post-canary 备份恢复。

完成标准：每个获批 live profile+instance 自身产生可追溯 evidence，无未批准来源，0 failed job，API 不可用时 Hermes 仍可对话，用户确认恒星、行星、关系和记忆治理可读。

E1 授权边界：readiness 门禁之前不得读取 Hermes profile 列表；门禁之后也不得生成新的 `hermes-production-*.env`、启动独立 Hermes HOME、改变来源角色或修改任一 Hermes 配置，直到用户确认 profile、instance、数据范围、模型范围、观察窗口和回滚点。rc.8 的容器重建/更新是另一个独立授权面。

## 4. 阶段 E2：真实数据质量校准（canary 内 P1）

- 以真实日常对话、工具确认和环境观察建立金标样本，分别计算事实准确率、证据可追溯率、重复率和虚假实体率。
- 校准长期/阶段/当前/低价值分类、休眠与唤醒阈值；不为增加显示数量降低证据门槛。
- 增加人际、项目、设备和服务关系样本，观察星系稳定性、重叠成员、桥接关系和单事实 clique 膨胀。
- 验证更正、脱离、忘记、永久清除、实体合并/拆分和 Vault grant/revoke 在真实数据上的派生重建。
- 每个调整批次单独提交、完整 Gate，生产候选只升级到明确验收的 revision。
- 使用质量报告的 `repeated_tool_event_groups`、`repeated_tool_event_copies` 审计历史
  重复证据；默认不删除只读 evidence。召回与浏览可合并同文展示，进一步隔离或清理由
  最新备份、影响清单和用户批准控制。

## 5. 阶段 E3：原地晋级与 V1.0 发布（被阶段 F Gate 阻断）

- rc.8 继续作为可回滚生产 canary，不因阶段 F 开发中断正常 Hermes 对话；
- 72 小时 canary、星图主观验收、最新备份恢复和安全检查通过；
- 阶段 F0–F8 全部完成，五个冻结场景通过，且 rc.8 备份升级/回滚演练 PASS；
- 用户给出可追溯批准参考，执行 `production-promote.sh`；
- 保持同一 database/Vault/namespace/project/image revision，生成 `PROMOTION-RECORD.json`；
- 生成版本 tag、源码包、校验和、镜像/SBOM 清单、升级/回滚说明和最终验收记录；
- 只有备份和用户确认后才退役旧测试/影子容器，不执行全局 Docker prune。

| G5-02 | 人工比例 Gate | 模型可处理金标样本中 `review` 比例不高于 10%，并分别报告误收、漏收、无效实体和重复率 |
| G6-01 | 生产授权 | 模型供应商/数据边界、密钥、费用、备份、候选清理、镜像 SHA 和回滚均单独批准后才可生产更新 |

## 8. 阶段 E4：稳定化与 V1 后续（P2）

| 方向 | 范围 |
| --- | --- |
| 多 profile 逐步扩大 | 每次只新增一个 profile，独立验证 source-bound evidence、观察窗口、同名恒星、跨 profile 召回和 Vault 权限 |
| 可观测性 | 健康、任务积压、失败/重试、数据增长、备份年龄、模型费用与脱敏计数 |
| 供应链强化 | 锁定构建工具，显式审核必要的 npm install script，生成 SBOM/签名和可验证发布清单 |
| 灾备与迁机 | 加密备份、Vault key 分离传输、目标主机离线恢复、切换窗口和禁止双写 |
| 通知与主动行为 | 整理报告渠道提醒；状态建议转行为仍需独立权限、渠道策略和审计 |
| V2 边界 | 多用户、多 Agent、云同步、外部知识源和通用 Agent 适配不进入 V1 稳定化补丁 |

## 10. 每个开发批次的固定流程

1. **范围确认**：只选择一个阶段中可独立验收的纵向切片，记录不做事项和生产边界。
2. **分支与基线**：从已通过 Gate 的 `main` 创建 `codex/` 分支，记录基线 SHA；不在生产 checkout
   临时修改。
3. **先测试后迁移**：先增加 schema/契约/负例测试，再实现 migration、repository、worker、API、
   Provider 和 UI；不把模型输出当唯一验收手段。
4. **本地测试梯度**：静态检查与单测 → migration → API/数据库 → Provider → 前端构建/浏览器
   → 故障恢复 → 备份恢复 → 完整 Release Gate。
5. **文档与 Review**：同步更新需求状态、API、迁移、运维、验收矩阵和变更报告；修复后再执行一次
   独立 Review，确认目标能力与“当前已实现”没有混写。
6. **提交与发布物**：提交保持单一目的；只有 CI/GHCR 完成并核对 full revision、双架构、SBOM 和
   attestation 后，才可成为部署候选。
7. **生产授权**：部署、migration、模型启用、历史导入、Hermes 配置变更和晋级分别授权，任一批准
   不自动包含其他动作。
8. **观察与回滚**：每次生产更新先备份、声明回滚点，更新后按来源观察并生成 post-canary 可恢复
   备份；发现主体错配、证据损坏、敏感泄漏或程序越权立即停止并回滚。
