# Agent Memory V1.0 GHCR 镜像发布与部署

## 1. 目标与边界

`main` 的 GitHub Actions 负责构建应用镜像并推送 GitHub Container Registry；
Hermes 所在生产主机只拉取已验证镜像，不再重复安装构建依赖或执行 Docker build。
工作流只发布镜像，不连接 Hermes、不修改生产 env、不重启生产容器。

API、worker、migrate 使用同一个 Dockerfile 和文件系统，仅入口命令不同。工作流因此只构建
一次，并把同一多架构 manifest 发布为三个包：

- `ghcr.io/evergardener/agent-memory-api`
- `ghcr.io/evergardener/agent-memory-worker`
- `ghcr.io/evergardener/agent-memory-migrate`

## 2. 发布触发与标签

`.github/workflows/quality.yml` 的 `publish-images` 只在以下条件同时满足时运行：

1. 事件为推送到 `main`，pull request 不发布；
2. `source-and-unit` 已通过 Ruff、完整 pytest、前端 check/build 和 shell 语法检查；
3. `GITHUB_TOKEN` 获得 job 级 `packages: write`；
4. Buildx 成功完成 `linux/amd64,linux/arm64` 构建并推送。

每个包发布两类标签：

- `sha-<40 位 Git revision>`：不可变部署身份，生产唯一允许值；
- `main`：便捷检查当前主线，允许移动，禁止生产使用。

应用版本仍由 `VERSION` 和镜像 OCI
`org.opencontainers.image.version` 表示。`AGENT_MEMORY_IMAGE_TAG` 与应用版本有意
解耦：本地隔离 Release 使用版本标签，生产使用提交 SHA 标签。

## 3. 供应链元数据

Buildx 以 `provenance: mode=max` 和 `sbom: true` 发布 OCI provenance 与 SBOM。
工作流另对三个包分别执行 GitHub artifact attestation，主题 digest 来自本次
`docker/build-push-action` 输出。镜像还包含：

- `org.opencontainers.image.source`
- `org.opencontainers.image.version`
- `org.opencontainers.image.revision`

构建参数不得传入密码、token 或 API key；max provenance 可能记录非秘密 build args。

## 4. 仓库和包的一次性设置

仓库 Actions 必须允许工作流使用 `GITHUB_TOKEN` 写 Packages。首次发布后检查三个 GHCR
包均关联本仓库。推荐把三个包设为 public，使生产主机无需保存 registry token。

若包保持 private，生产主机必须在执行部署前用最小 `read:packages` 凭据登录：

```bash
printf '%s' "$GHCR_READ_TOKEN" | docker login ghcr.io \
  --username '<github-user>' --password-stdin
unset GHCR_READ_TOKEN
```

只读 token 不写入 `production.env`、部署状态、日志或 Git。

## 5. 发布后验证

推送后必须确认 `source-and-unit`、`publish-images` 与 `verify-published-images` 均成功。
第三个 job 会从 GHCR 拉回三个精确 SHA 标签，核对双平台 manifest、attestation、
OCI version/revision，再以 `AGENT_MEMORY_SKIP_BUILD=1` 执行完整 Release Gate；
因此运行验证不会退回源码重建镜像。手工复核示例中的 revision 必须使用实际完整值：

```bash
revision="$(git rev-parse HEAD)"
for service in api worker migrate; do
  docker buildx imagetools inspect \
    "ghcr.io/evergardener/agent-memory-$service:sha-$revision"
done

gh attestation verify \
  "oci://ghcr.io/evergardener/agent-memory-api:sha-$revision" \
  --repo evergardener/agent-memory
```

任一包缺失、平台不完整、attestation 失败或 OCI revision 不匹配时，不进入生产变更窗口。

## 6. 生产使用

在目标 revision 的干净 checkout 中初始化新运行环境：

```bash
runtime_root="$HOME/.local/share/agent-memory/production"
bash scripts/init-production-env.sh "$runtime_root" "$runtime_root/production.env"
bash scripts/production-up.sh "$runtime_root/production.env"
```

初始化脚本固定写入：

```text
AGENT_MEMORY_IMAGE_PREFIX=ghcr.io/evergardener/agent-memory
AGENT_MEMORY_IMAGE_TAG=sha-<AGENT_MEMORY_REVISION>
```

启动脚本默认执行 Compose pull，随后逐个检查 API/worker/migrate 镜像的 OCI
version/revision，最后使用 `--no-build` 启动。首次验证后，本地 image ID 与 revision
继续被绑定进只读 deployment bundle。

生产升级仍需要单独授权、升级前恢复验证备份和回滚点；镜像发布成功不自动授权部署，也不允许
绕过现有 canary、来源策略或备份新鲜度门禁。

## 8. 已有生产运行态升级核对表

已有数据库的升级不是重新运行初始化脚本。固定目标 revision 后依次执行：

1. 确认 Actions 三个 job 全绿，并记录三个精确 SHA 镜像和 OCI revision；
2. 只读记录运行容器 revision、来源 inventory、namespace 和当前状态；
3. 使用当前已冻结运行资产创建并恢复验证切换前备份，保留旧镜像 ID 和旧 revision；
4. 把 `production.env` 的 revision/tag 与部署记录更新为同一个完整 SHA；
5. pull 精确镜像并执行迁移，使用专用升级模式启动，禁止本机 build：

   ```bash
   AGENT_MEMORY_PRODUCTION_SKIP_BUILD=1 \
     bash scripts/production-up.sh "$runtime_root/production.env" --upgrade
   ```

   `--existing` 只适用于 revision 未变化的重启；它必须拒绝缺失或不匹配的 manifest。
   `--upgrade` 先验证旧 bundle 与恢复验证备份，保留旧 revision，切换成功后生成并绑定
   新 revision 的只读 bundle；

6. 核对 API/worker/PostgreSQL、来源 inventory、failed jobs、星图及备份恢复；
   同时为新 revision 生成只读 deployment bundle，并在状态文件中绑定 manifest 路径与
   SHA-256；缺少绑定时标准 runtime Gate 必须失败关闭；
7. 对每个获批 Hermes profile 执行 `hermes-plugin.py upgrade --profile <name>`；
8. 结束旧 Agent 进程并新开 session，按 `current_state → write → browse → recall → trace`
   验收；
9. 记录切换时间、旧/新 revision、镜像 ID、备份和回滚点，生命周期状态默认保持
   `canary_active`。

若状态文件、env、实际容器和 Provider 任一项 revision/能力不一致，停止继续测试并先
修复漂移。`recall` 为空时先执行 `browse`；不得通过反复写入相同事实来“测试”。
